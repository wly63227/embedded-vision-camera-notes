# 机器人通信总线

## 接口选择

| 接口 | 典型用途 | 优势 | 风险 |
|---|---|---|---|
| I²C | 板内低速传感器 | 线少、带地址 | 上拉、总线卡死、距离短 |
| SPI | IMU、ADC、显示、Flash | 高速、时序直接 | 片选多、无标准设备协议 |
| UART | 调试、简单模块 | 易用 | 点对点、无天然帧边界 |
| CAN/CAN-FD | 电机与分布式节点 | 仲裁、抗干扰、错误检测 | 需要收发器和协议设计 |
| USB | MCU—主机 | 带宽高、供电方便 | 协议栈与枚举复杂 |
| Ethernet | 高带宽分布式系统 | 标准网络生态 | 实时性需额外设计 |

## 协议必须定义

- 版本、消息类型、长度、序号、时间戳。
- 字节序、单位、缩放、坐标系和有效范围。
- CRC/校验、超时、重试、幂等和兼容策略。
- 数据过期、丢包、乱序和节点重启的处理。

示例状态帧：

```text
SOF | VERSION | TYPE | LENGTH | SEQUENCE | TIMESTAMP | PAYLOAD | CRC
```

## CAN 设计要点

- ID 同时影响仲裁优先级，不要只把它当地址。
- 周期消息计算总线负载，给突发诊断留余量。
- 心跳只能证明节点还在发消息，不能证明功能正确。
- 命令要有超时；过期控制命令不得继续执行。

## 实验

1. UART 解析器通过半包、粘包、错误长度和错误 CRC 测试。
2. 两个 MCU 用 CAN 交换心跳、状态和控制命令。
3. 拔掉通信线，执行器在规定时间进入安全状态。
4. 人为提高总线负载，测量关键消息最大延迟。
