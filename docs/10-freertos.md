# 10｜FreeRTOS 基础与并发设计

## 何时使用 RTOS

当系统存在多个相对独立的时序活动、阻塞式外设、清晰的任务优先级或成熟中间件时，RTOS 能提高结构清晰度。简单系统若状态机已经可靠，不必为了“高级”而引入 RTOS。

## 核心对象

- Task：独立栈和调度状态的执行单元。
- Queue：复制消息，适合任务/ISR 间传递数据和所有权。
- Semaphore：计数事件或资源数量。
- Mutex：互斥访问共享资源，通常带优先级继承。
- Event Group：等待多个标志组合。
- Software Timer：在定时器服务任务上下文执行回调，回调必须短。

## 推荐架构

```text
采集任务 --sample queue--> 处理任务 --display queue--> 显示任务
                              |
                              +--telemetry queue--> 通信任务
```

优先用消息传递，减少共享可变状态。对每个队列定义容量、满时策略、消息所有权和最大等待时间。

## 优先级与阻塞

高优先级任务应等待事件，而不是忙等。优先级按“截止期限与响应要求”设计，不按模块重要程度命名。若高优先级任务持续可运行，低优先级任务会饥饿。

典型风险：

- 任务栈不足。
- 错误地从 ISR 调用普通 API。
- 持有互斥量时阻塞或调用不可控代码。
- 多把锁顺序不一致导致死锁。
- 队列满后永久等待形成级联阻塞。

## 时间与周期任务

周期任务优先使用绝对节拍语义（如 `vTaskDelayUntil`），减少漂移。把毫秒转换为 tick 时使用官方宏，并理解低 tick 频率的量化误差。

## 实验：三任务环境监测

- `sensor_task`：1 Hz 采样，通过队列发送不可变样本。
- `display_task`：消费最新样本，5 Hz 内刷新 UI。
- `command_task`：解析串口命令，可修改采样周期。
- 增加健康监控：检测任务超时、队列溢出和传感器错误。

## 验收标准

- 记录每个任务的最大栈使用量。
- 队列满、传感器超时、串口洪泛均有确定行为。
- 能解释互斥量与二值信号量的语义差别。
- 在 ISR 中使用对应的 `FromISR` API，并正确请求上下文切换。
